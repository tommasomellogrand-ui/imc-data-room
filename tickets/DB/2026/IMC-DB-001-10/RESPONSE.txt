VERDETTO:
IMC Ingestion & Provenance V1 può essere realizzata con UNA SOLA TABELLA persistente MySQL CORE:

`IMC Ingestion Provenance`

La tabella unica sostituisce operativamente la proposta a quattro tabelle di IMC-DB-001-08.

Il modello raccomandato è ibrido:
- RUN = una riga summary aggiornabile per ogni esecuzione;
- BATCH = una riga summary aggiornabile per ogni batch;
- ISSUE = riga append-only per warning/error/fatal;
- RECORD_EVENT = riga append-only SPARSE per skip/reject/conflict o lineage specificamente richiesto.

La V1 NON deve registrare un RECORD_EVENT per ogni inserimento riuscito.
Gli insert/update normali vengono sintetizzati nei counter RUN/BATCH.
Questo è il compromesso decisivo che rende sostenibile la tabella unica.

Principio di compatibilità:
- legacy/live business write path resta invariato finché il singolo importer non viene migrato;
- provenance shadow è aggiuntiva e non blocking;
- un failure della provenance NON blocca un importer non ancora V1-native;
- nessun importer deve conoscere DB/table SQL nel futuro V1-native;
- durante la transizione, i vecchi path restano disponibili finché esplicitamente certificati e cutoverati.

La prima implementazione raccomandata NON è una migrazione degli importer.
È:
PHASE 0 = creare soltanto `IMC Ingestion Provenance` e il registry V1 in codice, senza cambiare il comportamento di alcun importer.

Primo importer pilota successivo raccomandato:
Results, in modalità SHADOW.

6. IDEMPOTENCY MODEL
======================================================================

6.1 RUN IDEMPOTENCY

Non usare run_uuid come idempotency.
run_uuid identifica l'esecuzione, non il contenuto.

Ogni Repository Adapter definisce una Run Idempotency Policy.

Ordine di preferenza:
A. source_hash stabile + repository/GW/source scope;
B. importer-provided logical source key certificata;
C. repository-specific time/page/window key;
D. nessuna run-level dedupe blocking in SHADOW se l'identità non è affidabile.

Durante SHADOW:
la V1 NON deve impedire la run business solo perché non riesce a costruire un'idempotency key perfetta.

6.2 BATCH IDEMPOTENCY

batch_key stabile nell'ambito della run/source.
`dedupe_key = SHA256(RUN logical key + batch_key)` o equivalente adapter-defined.

Retry:
un nuovo run_uuid può riconoscere batch già completati in una run precedente tramite source identity + batch_key, ma soltanto dopo che l'adapter è certificato.

6.3 ROW IDEMPOTENCY

Non imporre una sola regola globale.

Policy:
- repository con fingerprint/natural key forte: usarli;
- repository con natural key ma senza fingerprint: natural key + normalized content hash;
- repository senza identity affidabile: lasciare il write/skip legacy invariato finché l'adapter non viene progettato e certificato.

6.4 DEDUPE KEY

`dedupe_key` è la protezione tecnica UNIQUE.
È prodotta dal runtime V1/adapter, non dal SQL client arbitrario.

6.5 RETRY

Nuovo run_uuid.
`retry_of_run_uuid` punta alla run precedente.
`attempt_no` incrementa.

Il retry può:
- riprocessare tutto in modalità safe-idempotent;
- oppure resume da batch specifico.

6.6 RESUME

Solo per adapter certificati.
La V1 legge i BATCH SUCCESS precedenti della stessa logical run identity e riparte dal primo batch non completato.

Per importer legacy/shadow:
nessun resume automatico nuovo viene introdotto.
Continua la logica corrente.

======================================================================
7. FAILURE POLICY
======================================================================

7.1 LEGACY / SHADOW IMPORTER

REGOLA OBBLIGATORIA:
PROVENANCE FAIL-OPEN rispetto al business write.

Sequenza raccomandata PHASE 1:
1. business write attuale;
2. risposta business calcolata;
3. tentativo best-effort di provenance RUN/BATCH;
4. se provenance fallisce:
   - NON rollback business data;
   - NON cambiare success response business;
   - log tecnico fallback su server/Action log;
   - metric alert `provenance_write_failure`.

La provenance non deve essere un prerequisito di un import non ancora V1-native.

7.2 V1_NATIVE IMPORTER FUTURO

Policy configurabile per repository:

STANDARD GAME-WORLD DATA:
preferenza = provenance-required ma con fallback controllato; valutare fail-closed solo dopo stabilità misurata.

CORE / MAPPING / GOVERNANCE-CRITICAL WRITES:
può essere ragionevole fail-closed se la Direzione richiede lineage obbligatorio.

Questa decisione NON va imposta globalmente nella V1 iniziale.

7.3 PROVENANCE FAILURE NON DEVE GENERARE RECURSION

Se `IMC Ingestion Provenance` non è scrivibile, non si tenta di loggare il failure nella stessa tabella in loop.
Fallback = application/server log esterno.

Solo dopo certificazione:
- ResultsAdapter diventa autoritativo per stable key/fingerprint handling;
- legacy read-before-write skip può essere rimosso gradualmente;
- write path può rimanere lo stesso physical repository.

Cutover separato e reversibile.

PHASE 4 · PROGRESSIVE ROLLOUT

Ordine suggerito:
1. Schedule
2. SM Player Stats
3. Transfers
4. Match Report
5. Player Codex
6. mapping/admin pipelines

L'ordine reale può cambiare sulla base di rischio/volume, ma ogni repository ha feature flag indipendente.

======================================================================
10. REGISTRY / GATEWAY MODEL
======================================================================

REGISTRY V1:
repository/config in GitHub, versionato.
Non tabella DB.

Ogni repository entry definisce almeno:
- repository_key;
- allowed GW scope;
- destination resolver;
- adapter class/version;
- importer compatibility mode;
- provenance_enabled;
- provenance_required;
- row_event_policy;
- idempotency policy name;
- transaction policy;
- max batch;
- retention profile.

LEGACY PATH

Rimane invariato.
Può continuare ad accettare i parametri che usa oggi finché quell'importer non è migrato.
Non va reso V1-compliant retroattivamente come prerequisito.

V1 SHADOW PATH

Il business write usa legacy/current path.
Il runtime identifica repository/GW/destination realmente utilizzati e registra provenance in best effort.

L'importer non è obbligato a inviare nuovi campi.
Se importer_name/version non sono disponibili, shadow usa fallback.

V1 NATIVE PATH

Input contiene SEMANTICA, non SQL routing libero:
- repository_key
- game_world_id
- source identity
- importer identity/version
- batch data

Registry risolve:
- database;
- table;
- adapter;
- validation/idempotency/write policy.

Il client NON può scegliere liberamente:
- target_database;
- target_table;
- SQL;
- DDL.

CRITERIO DI CUTOVER

Un importer passa a V1_NATIVE solo quando:
- shadow counters parity = PASS;
- idempotency candidate audit = PASS;
- performance regression accettabile;
- rollback testato;
- live verification positiva;
- esplicita certificazione importer-specifica.

======================================================================
11. RUN / BATCH STATE MACHINE
======================================================================

RUN:
RECEIVED
-> RUNNING
-> VALIDATING
-> WRITING
-> SUCCESS
   oppure PARTIAL
   oppure FAILED
   oppure CANCELLED

Non tutte le fasi devono essere materializzate come status intermedi se l'import dura pochi secondi.
La UI può mostrare solo lo stato corrente.

BATCH:
RECEIVED
-> VALIDATING
-> WRITING
-> SUCCESS
   oppure PARTIAL
   oppure FAILED

RETRY:
crea nuova RUN con:
- new run_uuid
- retry_of_run_uuid
- attempt_no + 1

Non resuscitare/modificare una run conclusa per rappresentare il retry.

======================================================================
12. ISSUE / WARNING MODEL
======================================================================

ISSUE è una riga event_type=ISSUE.

Campi principali:
- run_uuid
- parent_event_id
- batch_key
- repository_key
- game_world_id
- severity
- issue_code
- message
- record_key opzionale
- fingerprint opzionale
- metadata_json opzionale

SEVERITY:
INFO = diagnostica utile
WARNING = dato processabile con anomalia
ERROR = record/batch failure recuperabile
FATAL = run non può proseguire

RETRYABILITY:
Non aggiungere una colonna separata obbligatoria nella V1 minima.
Usare metadata_json.retryable boolean finché non emerge un uso query-heavy.
Se diventa metrica core, promuovere in colonna in un CASE futuro.

======================================================================
13. RECORD EVENT POLICY
======================================================================

DEFAULT:
NON registrare record event per ogni INSERT/UPDATE riuscito.

REGISTRARE SEMPRE SPARSE RECORD_EVENT per:
- SKIPPED quando serve spiegabilità;
- REJECTED;
- CONFLICT;
- record error;
- record lineage esplicitamente richiesto da adapter audit-critical.

REGISTRARE INSERTED/UPDATED per-record solo:
- debug temporaneo;
- mapping/governance con volumi bassi;
- repository per cui la Direzione richiede exact lineage.

Questo riduce la crescita di ordini di grandezza.

======================================================================
14. TABLE GROWTH / RETENTION
======================================================================

14.1 EVENTI SEMPRE REGISTRATI

Quando provenance è attiva:
- 1 RUN per esecuzione;
- 1 BATCH per batch effettivo;
- ISSUE solo quando esiste;
- RECORD_EVENT sparse.

14.2 RETENTION RACCOMANDATA

RUN:
24 mesi online.
Success summary leggere possono essere mantenute più a lungo se volume trascurabile.

BATCH:
12 mesi online.

ISSUE ERROR/FATAL:
24 mesi.

ISSUE WARNING:
12 mesi.

ISSUE INFO:
3-6 mesi.

RECORD_EVENT SKIPPED/REJECTED/CONFLICT:
12 mesi.

RECORD_EVENT success exact-lineage:
90 giorni default, salvo profilo repository diverso.

14.3 PURGE

Purge in chunk per created_at/event_type/status.
Non TRUNCATE globale.

Ordine consigliato:
1. vecchi RECORD_EVENT success;
2. INFO;
3. vecchi BATCH;
4. vecchie RUN solo dopo retention;
5. issue secondo policy.

parent_event_id senza FK permette purge indipendente.
run_uuid mantiene traccia logica anche se parent summary non è più online dopo anni.

14.4 ARCHIVE

Archive opzionale fuori CORE prima del purge:
JSONL/Parquet/object storage.
Non è richiesto nella V1 iniziale.

14.5 RAW PAYLOAD

Default:
NON salvare raw payload nella provenance.

Salvare:
- source_locator;
- source_hash;
- metadata minima.

Raw artifact eventuale:
fuori MySQL CORE, retention breve e solo per casi autorizzati.

15. QUERY EXAMPLES / LOGICHE OPERATIVE
======================================================================

A. ULTIMO IMPORT PER GW/REPOSITORY

SELECT *
FROM `IMC Ingestion Provenance`
WHERE event_type='RUN'
  AND repository_key=?
  AND game_world_id=?
ORDER BY started_at DESC, event_id DESC
LIMIT 1;

B. COUNTERS ULTIMA RUN

SELECT received_count,inserted_count,updated_count,skipped_count,
       rejected_count,warning_count,error_count,status,duration_ms
FROM `IMC Ingestion Provenance`
WHERE event_type='RUN' AND run_uuid=?;

C. PERCHÉ UNA RIGA È STATA SKIPPATA

SELECT record_key,record_outcome,issue_code,message,batch_key,created_at
FROM `IMC Ingestion Provenance`
WHERE event_type='RECORD_EVENT'
  AND repository_key=?
  AND game_world_id=?
  AND record_key=?
  AND record_outcome='SKIPPED'
ORDER BY created_at DESC;

D. ERRORI DI UNA RUN

SELECT severity,issue_code,message,batch_key,record_key,created_at
FROM `IMC Ingestion Provenance`
WHERE event_type='ISSUE'
  AND run_uuid=?
  AND severity IN ('ERROR','FATAL')
ORDER BY event_id;

E. BATCH FALLITI

SELECT event_id,batch_key,status,received_count,inserted_count,
       updated_count,skipped_count,rejected_count,error_count
FROM `IMC Ingestion Provenance`
WHERE event_type='BATCH'
  AND run_uuid=?
  AND status IN ('FAILED','PARTIAL')
ORDER BY event_id;

F. IMPORTER/VERSIONI CHE STANNO SCRIVENDO

SELECT importer_name,importer_version,gateway_version,
       COUNT(*) runs,MAX(started_at) last_seen
FROM `IMC Ingestion Provenance`
WHERE event_type='RUN'
  AND created_at >= NOW() - INTERVAL 30 DAY
GROUP BY importer_name,importer_version,gateway_version
ORDER BY last_seen DESC;

G. RETRY CHAIN

SELECT run_uuid,retry_of_run_uuid,attempt_no,status,started_at,completed_at
FROM `IMC Ingestion Provenance`
WHERE event_type='RUN'
  AND (run_uuid=? OR retry_of_run_uuid=? OR run_uuid IN (
       SELECT retry_of_run_uuid FROM `IMC Ingestion Provenance`
       WHERE event_type='RUN' AND run_uuid=?
  ))
ORDER BY attempt_no,event_id;

H. SITUAZIONE IMPORT GLOBALE PER GW/REPOSITORY

SELECT game_world_id,repository_key,
       MAX(started_at) last_run,
       SUM(inserted_count) inserted,
       SUM(updated_count) updated,
       SUM(skipped_count) skipped,
       SUM(rejected_count) rejected
FROM `IMC Ingestion Provenance`
WHERE event_type='RUN'
  AND started_at >= ?
GROUP BY game_world_id,repository_key;

Nota:
`IMC Repository Report` resta la source operativa autorizzata per le domande di inventario globale import correnti definite dalle regole IMC.
La provenance V1 non deve sostituire quel report finché non esiste un CASE esplicito di integrazione.

16. OBSERVABILITY
======================================================================

Derivabile direttamente dalla tabella unica:
- runs_total per repo/GW/importer/version;
- success/partial/failure rate;
- duration_ms;
- received/inserted/updated/skipped/rejected;
- warning/error/conflict rate;

- V1-native adoption rate;

- provenance logging failure repeated;
- importer version unknown sopra soglia;
- run FAILED ripetute;
- reject/conflict rate spike;
- run stuck RUNNING/WRITING oltre timeout;

======================================================================
17. TRANSACTION / PARTIAL FAILURE
======================================================================

SHADOW:
Business transaction è quella attuale.
Provenance è fuori dal critical path.

V1_NATIVE futuro:
Adapter dichiara transaction policy:
- ATOMIC_RUN
- ATOMIC_BATCH
- PARTIAL_ALLOWED

RUN/BATCH counters riflettono sempre ciò che è realmente committed.

Se un batch rollbacka:
- BATCH status=FAILED;
- inserted/updated committed = 0;
- issue registrata;
- RUN può continuare solo se adapter PARTIAL_ALLOWED.

Logical compensation:
NON progettare un generic rollback business universale.
Ogni eventuale compensazione è adapter-specific e va autorizzata separatamente.

======================================================================
18. SECURITY / SAFETY MODEL
======================================================================

V1_NATIVE:
- repository_key deve essere in registry;
- GW deve essere canonical/allowed;
- destination DB/table sono risolti server-side;
- action permessa dal registry;
- nessun SQL libero;
- nessun DDL runtime;
- nessun CREATE TABLE IF NOT EXISTS dinamico;
- nessun target non-IMC autorizzabile via input.

Database Manager resta l'unico percorso autorizzato per schema/migration.

SHADOW/LEGACY TRANSITION:
non si rompe il contratto attuale.
I path esistenti restano temporaneamente come sono.
La sicurezza V1-native non viene retro-imposta in una sola release causando outage.

Cutover per importer, non globale.

======================================================================
19. COMPROMESSI DELLA TABELLA UNICA
======================================================================

SVANTAGGI rispetto al modello a quattro tabelle:
- più colonne nullable;
- semantica dipende da event_type;
- vincoli DB specifici per tipo meno eleganti;
- RUN/BATCH summary e append-only event convivono;
- retention richiede predicate accurati.

VANTAGGI:
- una sola struttura CORE;
- query operative semplici;
- un solo schema/versioning path;
- una sola retention pipeline;
- nessun join cross-table necessario per dashboard base;
- minore superficie operativa;
- coerente con la decisione di CORE minimale;
- sufficiente se RECORD_EVENT resta sparse.

VALUTAZIONE:
Il compromesso è ACCETTABILE e raccomandato.

Condizione fondamentale:
NON trasformare la tabella in full row journal di tutti gli insert/update.
Se si registrasse una riga provenance per ogni record business riuscito, la soluzione a tabella unica diventerebbe inutilmente pesante.

- quattro tabelle Run/Batch/Issue/Record Event;

- metrics table separata;

- dynamic table creator;
- SQL-from-client ingestion;

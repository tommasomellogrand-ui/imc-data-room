3. B · CUS E COMPETITION KEY
======================================================================

ROOT CAUSE CUS:
CONFIRMED IMPORTER BUG + SOURCE TOKEN.

Il token CUS è realmente presente nel DOM GW001, nel pager e nell'onchange del division selector:
`MENU_competitionDivChange(..., 'CUS', 'league')`.

Nel mondo SINGLE questo token è un dettaglio tecnico Soccer Manager necessario alla navigazione, NON una dimensione semantica da persistere.

Errore corrente:
`context()` non distingue navigation context da canonical context.

Errore corrente 2:
`competitionKey()` serializza tutti i segmenti non vuoti:
`[gw,country,group,action,division].filter(clean).join('|')`.

Quindi una source token tecnica diventa automaticamente business semantics.

SPEC CANONICA:

SINGLE League:
`GW|DOMESTIC|league|division`
country persistito = NULL

SINGLE non-League DOMESTIC:
`GW|DOMESTIC|action`
country = NULL
division = NULL

INTERNATIONAL:
`GW|INTERNATIONAL|action`
country = NULL
division = NULL

NATIONS:
`GW|NATIONS|action`
country = NULL
division = NULL

MULTI League:
`GW|country|DOMESTIC|league|division`
country obbligatoria
division obbligatoria

MULTI DOMESTIC non-League country-scoped:
`GW|country|DOMESTIC|action`
division NULL, salvo regola canonica specifica autorizzata

Non usare `.filter()` come grammar engine.

9. H · IDEMPOTENCY FORENSIC
======================================================================

Comportamento corrente:
preloadExisting() costruisce:
- Set existingIds
- Set existingFingerprints

splitExisting():
SKIP se:
`existsById || existsByFingerprint`

Quindi:
- same ID + same fingerprint = skip corretto
- same ID + changed fingerprint = skip ERRATO ai fini remediation
- new ID + same fingerprint = skip senza distinguere duplicate content

PATCH SPEC:
preload deve costruire almeno:
`Map<sm_fixture_id, fingerprint>`
oltre a fingerprint set/map.

CLASSIFICAZIONE:

NEW
- fixture ID non esiste
- fingerprint non esiste

IDENTICAL
- fixture ID esiste
- fingerprint uguale

CHANGED_EXISTING
- fixture ID esiste
- fingerprint diverso

DUPLICATE_CONTENT
- fixture ID nuovo
- fingerprint già presente su altra fixture

TRANSITION POLICY:
- NEW -> insert
- IDENTICAL -> skip
- CHANGED_EXISTING -> NON update automatico in prima patch; log/segregate e conteggiare
- DUPLICATE_CONTENT -> warning/segregate

Una successiva remediation autorizzata potrà aggiornare CHANGED_EXISTING in modo controllato.

Questo mantiene idempotenza e impedisce che una patch corregga silenziosamente record storici senza autorizzazione.

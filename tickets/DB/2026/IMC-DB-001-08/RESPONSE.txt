======================================================================
0. EXECUTIVE RESULT
======================================================================

Questo CASE è stato eseguito esclusivamente in READ-ONLY / DESIGN-ONLY.
Nessuna tabella è stata creata.
Nessuna migration è stata eseguita.
Nessun codice è stato modificato.
Nessun deploy è stato eseguito.

CORE live verificato durante il CASE:
- 12 tabelle totali;
- 12 tabelle IMC;
- 0 tabelle non-IMC.

La V1 proposta NON è una resurrezione della vecchia ingestion.
È un nuovo sistema comune che governa l'ingresso verso repository IMC autorizzati mantenendo separati:
- transport/auth/routing;
- orchestration della run;
- contract/adapter del repository;
- validation;
- normalization/resolution;
- idempotency/skip;
- write;
- provenance/audit;
- issue/error handling.

Conclusione architetturale principale:
NON serve riscrivere tutti gli importer.
La strada più sicura è mantenere il loro lavoro di estrazione/parsing e sostituire progressivamente il tratto finale "read/skip/write" con un envelope V1 comune.

Il Universal Gateway attuale è riusabile come transport boundary, ma il path `IMPORT + route_mode=explicit` NON deve essere considerato il modello finale V1 perché oggi:
- il chiamante passa ancora `target_database` e `target_table`;
- l'ingress path accetta un namespace tabella più ampio dell'allowlist repository finale;
- fa INSERT puro;
- non gestisce update/skip/idempotency canonica;
- non registra una run persistente;
- non conosce importer/versione/source in modo strutturato;
- non ha adapter repository-specifici;
- restituisce `skipped_rows=0` per design, non perché abbia verificato idempotenza.

Il vecchio `__imc-sm-master/admin/ingestion/router.php` è attualmente hard-blocked con `legacy_core_removed` e NON deve essere riattivato.

======================================================================
A. EXECUTIVE ARCHITECTURE
======================================================================

TARGET LOGICO:

SOURCE / IMPORTER
    -> V1 INGESTION ENVELOPE
    -> AUTH + ALLOWLIST
    -> CREATE/RESUME INGESTION RUN
    -> REPOSITORY ADAPTER
    -> SCHEMA VALIDATION
    -> SEMANTIC VALIDATION
    -> REFERENCE RESOLUTION
    -> NORMALIZATION
    -> IDEMPOTENCY / SKIP DECISION
    -> AUTHORIZED IMC WRITE
    -> BATCH RESULT
    -> PROVENANCE / ISSUE LOG
    -> RUN FINALIZATION

Principio fondamentale:
L'importer NON sceglie database, tabella fisica o SQL.
L'importer dichiara soltanto:
- repository_key canonico;
- game_world_id quando pertinente;
- source identity;
- importer identity/version;
- source/run idempotency key;
- rows/batch.

Il repository registry V1 risolve internamente:
- database family;
- tabella fisica autorizzata;
- adapter;
- schema contract;
- row identity;
- idempotency policy;
- write policy;
- reference rules;
- transaction policy.

DDL è sempre fuori runtime ingestion.
Solo Database Manager può creare/modificare schema tramite CASE autorizzato.

======================================================================
C. PROPOSED DATA MODEL
======================================================================

Modello minimo consigliato: 4 entità persistenti.

1. `IMC Ingestion Run`
Una riga per esecuzione logica completa di un importer verso un repository.

2. `IMC Ingestion Batch`
Una riga per chunk transazionale della run.
Necessaria perché gli import correnti possono superare la dimensione di un singolo request e il Gateway attuale usa batch fino a 500 righe.

3. `IMC Ingestion Issue`
Una riga per warning/error/fatal issue a livello run/batch/record.
Sostituisce concettualmente la frammentazione dei vecchi error log senza copiarne il modello.

4. `IMC Ingestion Record Event`
Ledger SPARSE, non copia completa di ogni record.
Default: registra solo eventi che servono per spiegare una decisione row-level:
- skipped;
- rejected;
- warning;
- write error;
- update quando serve una provenance esatta;
- inserted solo per repository/modalità che richiedono exact-row lineage.

Questo modello è intenzionalmente ibrido:
- provenance persistente run/batch per tutto;
- provenance row-level solo quando aggiunge valore reale.

NON è proposta una tabella `Repository Registry` nel DB nella V1 iniziale.
Il registry deve essere codice/config versionato e allowlisted, perché rappresenta policy eseguibile e non dati business.

D. TABLES / ENTITIES PROPOSED
======================================================================

D1. IMC Ingestion Run
NECESSARIA: SI.
Perché senza una run persistente non possiamo rispondere in modo affidabile a quando/chi/cosa/quanto/esito.

D2. IMC Ingestion Batch
NECESSARIA: SI.
Perché serve retry/resume sicuro per import grandi e transaction boundaries realistiche.

D3. IMC Ingestion Issue
NECESSARIA: SI.
Perché warning/error/reject devono avere struttura coerente e interrogabile.

D4. IMC Ingestion Record Event
NECESSARIA: SI, ma SPARSE.
Perché skip/reject row-level richiedono motivo e record reference, senza salvare ogni payload intero.

D5. Repository Registry
NECESSARIA COME CONCETTO: SI.
PERSISTENTE IN DB: NO nella V1 iniziale.
TARGET: codice/config versionato nel repository GitHub.

D6. Raw Snapshot table
NECESSARIA: NO di default.
Non costruirla nella V1 base.

======================================================================
G. INGESTION RUN STATE MACHINE
======================================================================

Stati consigliati:

RECEIVED
-> VALIDATING
-> READY
-> WRITING
-> COMPLETED

Varianti terminali:
- COMPLETED_WITH_WARNINGS
- PARTIAL
- FAILED
- ABORTED

Stato retry operativo:
- RETRY_PENDING
- RESUMING

Regole:

RECEIVED
Envelope autenticato e run creata/resolta.

VALIDATING
Repository, GW, source/importer metadata e batch contract in validazione.

READY
Envelope e contract validi, write non ancora iniziata.

WRITING
Uno o più batch in elaborazione.

COMPLETED
Tutto ciò che era eleggibile è stato processato senza warning/error bloccanti.

COMPLETED_WITH_WARNINGS
Write completata ma esistono warning non bloccanti.

PARTIAL
Almeno un batch committato e almeno un batch fallito/non completato in modalità partial/batch atomic.

FAILED
Nessun risultato valido committato oppure failure bloccante in modalità all-or-nothing.

ABORTED
Stop amministrativo esplicito prima del completamento.

RETRY_PENDING / RESUMING
Retry controllato della stessa run logica o di una run collegata.

Transizioni illegali devono essere rifiutate.

======================================================================
H. PROVENANCE STRATEGY
======================================================================

STRATEGIA RACCOMANDATA: IBRIDA.

RUN LEVEL: sempre.
Conserva:
- source;
- importer/version;
- repository;
- GW;
- start/end;
- status;
- counters;
- idempotency.

BATCH LEVEL: sempre per import multi-batch.
Conserva retry/resume e transaction boundary.

ROW LEVEL: sparse.
Conserva solo ciò che è utile per spiegare una decisione o riprodurre un problema.

Perché NON loggare ogni riga sempre:
- Results/Schedule/Stats possono crescere molto;
- duplicheremmo chiavi/fingerprint già nei repository;
- il CORE audit diventerebbe più grande dei dati business;
- retention diverrebbe costosa.

Quando abilitare exact-row lineage:
- import sensibili/manuali;
- mapping globali;
- migrazioni one-shot;
- troubleshooting;
- repository senza una chiave/fingerprint nativa sufficiente.

======================================================================
J. IDEMPOTENCY / SKIP MODEL
======================================================================

Due livelli distinti.

1. RUN IDEMPOTENCY
Chiave composta logicamente da:
repository_key + scope_key + idempotency_key.

L'idempotency_key può derivare da:
- source fingerprint;
- source date/version;
- importer supplied stable key;
- combinazione deterministica autorizzata dall'adapter.

Stessa run idempotency:
- se COMPLETED: rispondere already_completed / no-op;
- se WRITING: reject/concurrency conflict;
- se PARTIAL/FAILED retryable: resume/retry secondo policy.

2. ROW IDEMPOTENCY
Definita dall'adapter.

L'adapter restituisce una decisione:
- INSERT
- UPDATE
- SKIP_EXACT
- SKIP_STALE
- REJECT_CONFLICT

Il Gateway non inventa questa decisione.

Fingerprint:
- usato quando il repository ha contenuto mutable o quando la natural key da sola non distingue versioni;
- non obbligatorio universalmente.

Esempi compatibili con strutture attuali:

Results:
- sm_fixture_id + fingerprint sono già concetti presenti nel repository;
- adapter deve distinguere fixture già identica da stessa fixture con contenuto differente.

Schedule:
- fixture identity/stable key come base;
- skip se record equivalente già presente;
- update solo se contract lo autorizza.

Match Report:
- natural identity primaria: game_world_id + sm_fixture_id;
- fingerprint come verifica di contenuto quando disponibile.

Transfers:
- usare la chiave canonica già definita dal repository/importer, non dedup generico del Gateway.

Player Codex:
- current profile tipicamente upsert per player identity;
- history/eventi hanno chiavi dedicate e separate.

SM Player Stats:
- adapter deve definire identity per player + competition/scope canonico e la semantica snapshot/update.

======================================================================
L. SECURITY / ALLOWLIST MODEL
======================================================================

1. Il client NON può inviare:
- SQL;
- target_database;
- target_table fisica;
- arbitrary action;
- DDL.

2. Envelope accetta solo repository_key allowlisted.

3. Registry versionato risolve:
repository_key -> adapter -> destination family/table.

4. V1 runtime DB user dovrebbe avere privilegi minimi:
- SELECT sui parent/reference necessari;
- INSERT/UPDATE sulle sole destinazioni autorizzate;
- INSERT/UPDATE sulle 4 tabelle V1 audit;
- NO CREATE;
- NO ALTER;
- NO DROP;
- NO TRUNCATE;
- NO GRANT.

5. Database Manager usa un percorso/ruolo separato.

6. Game World validation obbligatoria contro IMC Game World Codex Global.

7. Batch limits:
- max rows;
- max request bytes;
- max JSON nesting;
- timeout.

8. Importer identity/version mandatory.

9. Trace/run UUID in ogni response.

10. Nessun token/segreto nei log o details_json.

11. Unknown repository/action = reject, mai fallback dinamico.

12. La regex `GWxxx_IMC <qualcosa>` da sola NON è sufficiente come allowlist V1.

======================================================================
M. RAW PAYLOAD + RETENTION POLICY
======================================================================

DEFAULT:
NON conservare raw payload nel CORE.

Conservare:
- source fingerprint;
- source locator;
- counts;
- record keys;
- issue details bounded;
- eventuale tiny excerpt redatto solo per error diagnosis.

Raw snapshot opzionale solo quando:
- fonte non è ripetibile;
- audit/replay è business-critical;
- CASE/import esplicitamente lo richiede;
- errore complesso necessita forensic replay.

Se necessario:
- storage fuori dalle tabelle CORE business;
- object/file storage privato o artifact storage;
- hash nel Run;
- retention corta.

Retention proposta:

Run:
- 24 mesi minimo per summary audit;
- success run può essere mantenuta più a lungo perché leggera.

Batch:
- 12 mesi;
- success batch aggregabile/purgabile dopo retention.

Issue ERROR/FATAL:
- 12-24 mesi.

Warning:
- 6-12 mesi.

Record Event successful exact-lineage:
- 90-180 giorni salvo repository sensibile.

Record Event skip/reject/error:
- 12 mesi.

Raw artifact:
- default 0 giorni perché non creato;
- se creato per debug: 7-30 giorni;
- se audit-critical: retention esplicitamente autorizzata per CASE.

======================================================================
O. CURRENT IMPORTERS MIGRATION PATH
======================================================================

AUDIT CURRENT STATE

1. UNIVERSAL GATEWAY
Versione runtime nel codice: 2.2.13.
Supporta IMPORT/CHATGPT.
Esiste già un ramo `IMPORT + route_mode=explicit`.

Punto positivo:
- trasporto già centralizzato;
- routing GW/DB già noto;
- request/response JSON già usato;
- batch insert e transaction support esistenti;
- schema/type validation esiste nel core tradizionale;
- alcuni repository hanno strict validators dedicati.

Limiti incompatibili col target V1:
- ingress explicit riceve target_database/target_table;
- target table ingress è validata con regex/prefix, non solo registry semantico;
- insert-only;
- nessun run persistence;
- nessun adapter contract;
- nessun update/skip engine;
- nessun importer/source version model strutturato;
- nessuna provenance batch/row persistente.

2. RESULTS
Stato osservato:
- supportato come repository import dal Universal Gateway;
- import table con schema/type validation;
- concetti fingerprint/sm_fixture_id già esistono nel dominio.

Migrazione V1:
- lasciare invariato extraction/parsing;
- sostituire envelope finale con repository_key=results;
- spostare row idempotency/semantic validation nel ResultsAdapter;
- importer può mantenere temporaneamente il proprio read-before-write skip durante fase 1, ma deve diventare non-autoritativo e poi essere rimosso.

3. SCHEDULE
Stato osservato:
- repository supportato dal Gateway;
- generic import validation attuale.

Migrazione V1:
- payload sostanzialmente invariato;
- ScheduleAdapter definisce stable identity e update policy;
- nessuna necessità di riscrivere la navigazione Soccer Manager.

4. MATCH REPORT
Stato osservato:
- supportato dal Gateway;
- strict validator corrente controlla struttura esatta;
- payload corrente include identity competizione, fixture, score, 5 JSON, fingerprint/imported_at.

Migrazione V1:
- spostare l'elenco campi e regole dal Gateway core al MatchReportAdapter;
- mantenere one-row-per-fixture dove applicabile;
- natural identity game_world_id + sm_fixture_id;
- fingerprint per content equivalence/conflict;
- nessuna mega-riscrittura importer.

5. TRANSFERS
Stato osservato:
- strict validator corrente nel write path;
- struttura repository specifica già separabile.

Migrazione V1:
- spostare contract nel TransfersAdapter;
- mantenere parser/browser logic;
- adapter governa identity, duplicate semantics e import number;
- importer non deve più inviare target table/database.

6. PLAYER CODEX
Stato osservato:
- strict validator dedicato esiste per GW Player Codex;
- CORE possiede inoltre Player Codex Global/Data/Rating History canoniche.

Migrazione V1:
- PlayerCodexAdapter deve distinguere current profile, world-scoped profile e history/event semantics;
- non usare un generico upsert per tutte le componenti;

======================================================================
T. TRANSACTION / PARTIAL FAILURE POLICY
======================================================================

Default raccomandato:
ATOMIC_BATCH.

Perché:
- limita rollback size;
- permette resume;
- scala meglio;
- mantiene consistenza locale.

ATOMIC_RUN:
solo dataset piccoli/identity-critical quando adapter lo dichiara.
Esempio plausibile: mapping piccoli.

PARTIAL_ALLOWED:
solo repository dove record indipendenti possono essere accettati senza compromettere coerenza.

Regole retry:
- non reinserire batch già COMPLETED;
- batch idempotency impedisce doppio commit;
- retry solo failure retryable;
- record reject non retryable resta reject finché source/contract cambia;
- retry genera attempt increment o run collegata secondo failure stage.

Logical compensation:
NON automatica in V1 base.
Un batch già committato non viene cancellato genericamente se un batch successivo fallisce.
Compensation è adapter-specific e deve essere esplicitamente autorizzata.

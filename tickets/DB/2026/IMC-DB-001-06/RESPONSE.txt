0. EXECUTIVE RESULT
======================================================================

Il CASE è stato eseguito esclusivamente in READ-ONLY.
Nessuna tabella/colonna/migration/codice/deploy è stata creata o modificata.

Stato CORE verificato:
- 11 tabelle totali;
- 11 tabelle IMC;
- 0 tabelle non-IMC;
- 68 colonne complessive nelle 11 IMC;
- 2 FK IMC->IMC;
- nessuna colonna JSON nelle 11 IMC attuali.

Conclusione principale:
NON esistono sei nuovi blocchi DB da ricostruire.
Le sei aree residue si dividono così:
- 1 area ALREADY COVERED;
- 2 aree PARTIALLY COVERED;
- 0 aree NOT COVERED ma già tecnicamente dimostrate come indispensabili;
- 1 area NOT NECESSARY come struttura separata;
- 2 aree NEEDS DIRECTOR DECISION.

Il risultato più importante è che il CORE attuale contiene già molta più semantica utile di quanto implicassero i vecchi nomi legacy. In particolare:
- il Competition Codex copre già la maggior parte della funzione operativa del vecchio meta-layer;
- il Player Codex applicativo può essere ricostruito come ACCESS/RESOLUTION layer sulle tre IMC Player esistenti, senza nuovo schema;
- il club mapping esiste già come membership per-GW, ma è incompleto come copertura dei Game World e non dimostra l'esistenza di un identificativo world-local distinto;
- il national team world-local mapping non è presente, ma la sua necessità di prodotto non è ancora dimostrata al di fuori dei consumer legacy/guarded;
- season/context è l'unico vero DATA GAP strutturale già visibile se si vuole mantenere una funzione season-aware;
- ingestion/provenance è soprattutto una decisione di modello operativo: il CORE deve essere aggiornato automaticamente/auditably oppure mantenuto come catalogo canonico curato?

2. AREA A · WORLD-LOCAL CLUB MAPPING
======================================================================

1. AREA
WORLD-LOCAL CLUB MAPPING

2. OLD/RESIDUAL NEED
Il vecchio modello usava un mapping club globale -> identificativo club nel Game World per Team Hub, API, enrichment e ingestion.

3. CURRENT PRODUCT NEED
Consumer correnti nel repository continuano a contenere riferimenti al vecchio clubs_game_world_id, in particolare:
- api/imc-gateway/team-hub.php;
- site-assets/master/api.php;
- api/imc-data/v1/index.php.
Il Team Hub è oggi protetto da core_mapping_rebuild_required; quindi il bisogno non è soltanto teorico, ma una capability attualmente disabilitata.
Parte dell'ingestion che usava il mapping è invece legacy/bloccata e non va presa come prova di necessità.

4. IMC COVERAGE
IMC Game World Club Mapping copre già:
- Game World;
- Club ID globale;
- Club Name;
- SM Club ID.
IMC Club Codex Global copre identità e asset.
IMC Game World Codex Global copre il parent GW.

5. COVERAGE LEVEL
PARTIAL.

6. REAL GAP
DATA GAP:
- mancano le membership di GW007, GW008 e GW010 nella mapping corrente (1.020 club attivi complessivi secondo Game World Codex).
- non esiste evidenza nel CORE di un identificativo world-local distinto da Club ID/SM Club ID: nelle 1.434 righe presenti i due ID sono sempre uguali.

ACCESS GAP:
- i consumer legacy/current non sono stati ancora riscritti per usare IMC Game World Club Mapping.

Non è quindi dimostrato che serva una NUOVA struttura. Prima va verificato se `SM Club ID` è semanticamente sufficiente per l'identità richiesta dai consumer moderni.

7. CONSEQUENCE OF DOING NOTHING
- Team Hub club dataset resta bloccato;
- alcuni enrichment/API che si aspettano un local club ID restano non funzionanti;
- le 1.434 membership esistenti restano comunque disponibili.

8. NECESSITY CLASSIFICATION
PARTIALLY COVERED.

9. RECOMMENDATION
REUSE EXISTING prima di costruire qualsiasi nuova tabella.
FUTURE MINIMAL ADDITION solo se una verifica delle fonti correnti dimostra che esiste davvero un ID per-GW distinto da `SM Club ID`.
Completare la copertura GW007/GW008/GW010 è prima di tutto un data-population gap, non una prova di schema insufficiente.

10. PRIORITY
HIGH, perché una capability prodotto è attualmente guarded.

GAP TYPE:
DATA GAP + ACCESS/RESOLUTION GAP.

6. AREA E · INGESTION & PROVENANCE V2
======================================================================

1. AREA
INGESTION & PROVENANCE V2

2. OLD/RESIDUAL NEED
La vecchia pipeline manteneva snapshot sorgente, raw/source tables, canonical rebuild, import errors e ingestion audit.
È stata intenzionalmente bloccata da IMC-DB-001-05 per impedire la ricreazione legacy.

3. CURRENT PRODUCT NEED
Il CORE contiene dati che per loro natura possono richiedere aggiornamenti nel tempo:
- Player Data updated_at massimo 2026-09-10 10:15:58;
- Rating History imported_at massimo 2026-09-10 10:15:32;
- Game World / Club / Manager / Competition Codex sono cataloghi operativi.
Quindi una capacità di aggiornamento futura può essere utile.
Ma il prodotto runtime non necessita di source_snapshots/raw source tables per LEGGERE i dati correnti.
La necessità di una pipeline automatica/auditabile è una scelta operativa, non una conseguenza obbligatoria del modello dati.

4. IMC COVERAGE
Le 11 IMC coprono il dato canonico finale.
Provenance attuale disponibile soltanto in forma minima:
- Player Data.updated_at;
- Rating History.imported_at.
Non esiste audit generale di origine/import per gli altri Codex.

5. COVERAGE LEVEL
FULL per storage canonico corrente;
NONE per una pipeline generale di provenance/ingestion audit.

6. REAL GAP
PROCESS/OPERATIONAL GAP, non necessariamente DATA GAP:
- nessun flusso CORE V2 autorizzato oggi aggiorna automaticamente le 11 IMC da fonti esterne;
- nessun lineage generale indica source/run/hash/import per tutte le entità.

7. CONSEQUENCE OF DOING NOTHING
- il CORE resta leggibile e funzionale come snapshot canonico;
- i dataset che richiedono refresh non si aggiornano automaticamente tramite la pipeline legacy, che è correttamente bloccata;
- la tracciabilità di origine resta limitata.

8. NECESSITY CLASSIFICATION
NEEDS DIRECTOR DECISION.

Decisione binaria proposta:
"Il CORE deve essere aggiornato automaticamente e con audit/provenance da sorgenti esterne, oppure può essere mantenuto come catalogo canonico aggiornato da processi specifici/curati?"
- catalogo curato/specific updates -> nessun nuovo layer provenance obbligatorio;
- auto-ingestion auditabile -> serve una nuova capability applicativa, ma NON è ancora dimostrato che richieda nuove tabelle DB.

9. RECOMMENDATION
DIRECTOR DECISION.
Non progettare schema finché non è deciso il modello operativo.

10. PRIORITY
HIGH come decisione operativa; NONE per schema finché la decisione non è presa.

MINISITE CORE · UX FAMILY ARCHITECTURE CONVERGENCE AUDIT

1. EXECUTIVE VERDICT

La decisione della Direzione è tecnicamente coerente e richiede una precisazione importante rispetto a IMC-ENG-009 e IMC-ENG-009-01.

Non basta più pensare:

ONE CORE
+ GW CONFIG
+ GW THEME

La struttura definitiva raccomandata diventa:

ONE IMC MINISITE CORE
→ TWO UX FAMILY CONTRACTS
   → SINGLE FAMILY
   → MULTI/GOLD FAMILY
→ GW CREATIVE PACKAGE
→ OPTIONAL FEATURES / SIGNATURE COMPONENTS

Il Core resta uno solo e non conosce GW specifici.
Le due famiglie NON sono due codebase: sono due contratti dichiarativi/comportamentali sopra lo stesso Core.
Il GW package continua a possedere identità, composizione, rendering, theme, typography, motion, asset e storytelling.

Formula definitiva:

CORE OWNS UNIVERSAL BEHAVIOR
UX FAMILY OWNS CROSS-GW PREDICTABILITY
GW PACKAGE OWNS CREATIVE IDENTITY
FEATURES OWN OPTIONAL CAPABILITIES

La famiglia SINGLE assume GW001 come riferimento UX fondativo.
La famiglia MULTI/GOLD assume GW007 come riferimento UX fondativo, generalizzandone il principio dei quattro ingressi prioritari attraverso una Top-4 Country dinamica derivata dai manager IMC attivi.

Questa convergenza è realizzabile senza degradare GW001 e senza banalizzare GW007 a normale Country UX, a condizione che il confine fra FAMILY CONTRACT e CREATIVE FREEDOM sia formalizzato prima dell'implementazione.

2. MODELLO ONE CORE / TWO UX FAMILIES

L'architettura raccomandata ha quattro livelli.

LIVELLO 1 · UNIVERSAL CORE
Responsabile di:
- bootstrap;
- route engine;
- navigation state;
- URL/deep-link parsing;
- context state/persistence;
- data access;
- loading/error/empty/not-found;
- focus/keyboard/accessibility behavior;
- responsive state primitives;
- capability registry;
- semantic component models;
- lifecycle;
- telemetry/test hooks.

Il Core non conosce SINGLE, MULTI o GW specifici come branching procedurale. Conosce soltanto contratti registrati.

LIVELLO 2 · UX FAMILY CONTRACT
Due registry/configurazioni di famiglia:
- SINGLE;
- MULTI_GOLD.

La family definisce ciò che un manager deve ritrovare prevedibilmente passando da un GW della stessa famiglia a un altro:
- primary destinations;
- navigation placement/behavior contract;
- context hierarchy;
- mobile navigation pattern;
- deep-link/back rules;
- entry-point semantics;
- required shared capabilities;
- minimum information hierarchy.

La family NON definisce:
- palette;
- typography;
- materials;
- visual hierarchy interna delle composizioni;
- hero;
- score skin;
- motion grammar;
- editorial pacing.

LIVELLO 3 · GW CREATIVE PACKAGE
Responsabile di:
- theme;
- renderer registry;
- composition;
- typography;
- motion;
- imagery/assets;
- creative tokens;
- signature components;
- editorial storytelling;
- local feature enablement.

LIVELLO 4 · OPTIONAL FEATURE MODULES
Capability sportive/editoriali riusabili:

- promotion/relegation;
- progression;
- comparison;

- reports.

La family può richiedere una capability minima; il GW decide come renderizzarla.

3. SINGLE UX FAMILY CONTRACT

GW001 diventa il reference implementation funzionale della famiglia SINGLE, non un template grafico.

ELEMENTI OBBLIGATORI DA STANDARDIZZARE PER TUTTI I SINGLE

A. PRIMARY DESTINATIONS
Devono essere semanticamente stabili e immediatamente riconoscibili:
- Home;
- Competitions;
- Results;
- Schedule;
- Standings;
- Clubs;
- Managers;
- Players;
- Transfers;
- More/Archive/Data/Reports quando presenti.

Non è necessario mostrarli tutti contemporaneamente nella primary nav, ma il loro significato e accesso devono essere prevedibili.

B. COMPETITION-FIRST INFORMATION MODEL
Gerarchia minima:
GAME WORLD
→ COMPETITION / DIVISION quando pertinente
→ CONTENT
→ DETAIL.

Il Single non introduce Country artificiale.

C. MATCH AS FIRST-CLASS OBJECT
Results e Schedule devono condurre a un Match Detail/Match Center coerente semanticamente.
Il match non è soltanto una riga di score: può avere source state, competition context, clubs, manager/player data, report, timeline/statistiche quando disponibili.

D. HUB → DETAIL PATTERN
Competition, Club, Manager, Player e Match devono avere route/detail semanticamente stabili.

E. ARCHIVE/NARRATIVE COMPATIBILITY
La famiglia deve consentire che il contenuto sportivo diventi memoria/storia, come in GW001. Archive non è obbligatorio per ogni GW, ma il Core/family non deve impedirne la profondità narrativa.

F. NAVIGATION PREDICTABILITY
Desktop e mobile devono conservare le stesse destinazioni fondamentali e regole di back/deep-link.
Il rendering della navigation può cambiare entro il Creative Freedom Contract, ma posizione e comportamento fondamentali della family devono restare riconoscibili.

G. MOBILE CONTRACT
Home, Results, Schedule e Standings devono essere accessibili con pattern di primo livello coerente nella famiglia; More raccoglie destinazioni secondarie.

H. CONTEXT
Se il Single usa divisioni o competition scope, il contesto deve persistere durante la navigazione quando semanticamente valido.

4. MULTI/GOLD UX FAMILY CONTRACT

GW007 diventa il reference UX fondativo per il principio degli ingressi prioritari e della navigazione per contesto.

ELEMENTI OBBLIGATORI DA STANDARDIZZARE PER TUTTI I MULTI/GOLD

A. FOUR PRIMARY CONTEXT ENTRIES
La superficie primaria presenta esattamente quattro ingressi prioritari quando i dati lo permettono.

Per GW007:
- gli ingressi restano i quattro Kingdom fondativi definiti dal concept.

Per gli altri MULTI/GOLD:
- gli ingressi sono i quattro Country con maggior numero di manager IMC attivi nel Game World.

B. COMPLETE CONTEXT ACCESS
I Country non Top-4 restano sempre raggiungibili tramite selector/menu/index completo.
La Top-4 è priorità, non filtraggio del mondo.

C. CONTEXT HIERARCHY
Per MULTI standard:
WORLD
→ COUNTRY
→ DIVISION
→ COMPETITION
→ CONTENT.

Per GW007:
WORLD
→ KINGDOM/TERRITORY
→ DIVISION/COMPETITION secondo il modello del GW
→ CONTENT.

Il Core tratta Country e Territory come context dimensions con contratti diversi; non rinomina una stringa.

D. PERSISTENT CONTEXT
Country/Territory e Division devono essere URL-preserved e mantenuti tra Results, Schedule, Standings e altre destinazioni compatibili.

E. FAMILY NAVIGATION
Le destinazioni fondamentali e il comportamento della primary navigation devono restare nello stesso luogo/logica all'interno della famiglia.
La creatività può cambiare skin e composizione interna, non spostare arbitrariamente l'accesso fondamentale da un'estremità all'altra del prodotto.

F. MOBILE
Bottom/primary mobile navigation coerente nella famiglia:
Home
Results
Schedule
Standings
More

Il Context Selector resta sempre visibile/raggiungibile senza gesture occulte.

G. CONTEXT-FIRST ENTRY
L'utente deve capire in quale Country/Kingdom/Division sta operando prima di interpretare Results, Schedule o Standings.

5. DYNAMIC TOP-4 COUNTRY MODEL

La Top-4 deve essere una capability shared del MULTI/GOLD family layer, non codice locale dei singoli GW.

5.1 INPUT SEMANTICO

Serve un dataset di manager assignment attivi per Game World contenente almeno:
- game_world_id;
- manager_id;
- assignment_type;
- club_id;
- start_date;
- end_date;
- Country del club/assignment, direttamente o derivabile tramite mapping autorevole.

Il modello deve utilizzare esclusivamente manager IMC attivi nel GW.

Definizione raccomandata di ACTIVE:
- assignment appartenente al game_world_id corrente;
- assignment di club valido per il ranking Country;
- start_date <= data di riferimento;
- end_date assente o >= data di riferimento;
- manager_id valido e appartenente al Manager Codex IMC.

Questa definizione deve essere formalizzata nel data contract e non reinventata nel frontend.

5.2 PIPELINE

Manager Assignments
→ filter ACTIVE
→ join Club/Country mapping
→ group by Country
→ distinct manager_id per Country
→ count
→ deterministic sort
→ first four
→ Family Context Entries.

Il conteggio deve usare manager distinti, non assignment rows, per evitare doppio conteggio in presenza di duplicazioni/storico.

5.3 NO HARDCODING

Il frontend non contiene:
Italia, Francia, Germania, Belgio.

Riceve un view model:
[
  {contextId, label, activeManagerCount, rank},
  ...
]

generato dal family data selector/shared domain function.

Nessun if(GW002), if(GW003), ecc.

GW007 non usa questo selector per scegliere i quattro Kingdom: la sua config dichiara un context provider di tipo FIXED_TERRITORY_SET perché i quattro Kingdom sono struttura fondativa del prodotto. È una capability dichiarativa generale, non branching sul GW.

Quindi il family contract supporta due provider:
- RANKED_ACTIVE_MANAGER_COUNTRIES;
- FIXED_CONTEXT_SET.

5.4 FALLBACK < 4 COUNTRY ATTIVI

Ordine raccomandato:
1. mostrare tutti i Country con almeno un manager IMC attivo;
2. completare fino a quattro con Country esistenti nel Game World ordinati deterministicamente per rilevanza strutturale disponibile;
3. marcare gli entry supplementari come 0 manager attivi senza inventare attività;
4. se il Game World possiede in totale meno di quattro Country, mostrare il numero reale di entry senza creare placeholder fittizi.

Per la rilevanza strutturale di fallback, preferenza:
- numero di club attivi nel Country;
- poi numero di divisioni/competizioni;
- poi ordine alfabetico normalizzato.

Il fallback deve essere dichiarato nel contratto e testato.

5.5 PARITÀ

Sort deterministico raccomandato:
1. active_manager_count DESC;
2. active_club_count DESC, se disponibile;
3. normalized_country_name ASC;
4. stable_country_id ASC.

La parità non deve dipendere dall'ordine restituito dal DB.

5.6 STALE/MISSING DATA

Se il dato manager assignment non è disponibile:
- non inventare una Top-4;
- mostrare fallback strutturale dichiarato con stato informativo;
- registrare data state = degraded;
- mantenere accessibile l'intero Country selector.

17. RISCHI E TRADE-OFF

RISCHIO 1 · FAMILY CONTRACT TROPPO VISUALE
Se impone markup/layout, distrugge la libertà creativa.
Mitigazione: family contract definisce destination/behavior/placement semantics, non skin/layout interno.

RISCHIO 2 · FAMILY CONTRACT TROPPO DEBOLE
Se dice soltanto quali route esistono, i manager continueranno a trovare menu e comportamenti diversi.
Mitigazione: formalizzare primary navigation placement/behavior e mobile contract.

RISCHIO 3 · TOP-4 INSTABILE
Ingressi che cambiano continuamente possono disorientare.
Mitigazione: derivazione deterministica; eventuale snapshot/cache per sessione/release; mostrare conteggio manager e accesso completo agli altri Country.

RISCHIO 4 · DATI MANAGER NON AFFIDABILI
Assignment incompleti produrrebbero priorità errate.
Mitigazione: data quality state e fallback strutturale trasparente.

RISCHIO 5 · GW007 TRATTATO COME ECCEZIONE HARDCODED
Mitigazione: provider generale FIXED_CONTEXT_SET + context type TERRITORY.

RISCHIO 6 · GW001 RISCRITTO TROPPO PRESTO
Mitigazione: golden master, adapter-first, zero redesign nel pilot.

RISCHIO 7 · FEATURE EXTRACTION PREMATURA
Mitigazione: estrarre una feature shared quando esiste almeno un secondo consumer reale o un contratto chiaramente universale.

RISCHIO 8 · TROPPI LAYER
Core + family + feature + GW package può diventare burocratico.
Mitigazione: ogni layer deve possedere una responsabilità esclusiva e piccola; niente framework/plugin system generale oltre i bisogni osservati.

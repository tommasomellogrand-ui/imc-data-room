ARCHITETTURA SCELTA
V1 file-based e deterministica. GitHub tommasomellogrand-ui/imc-data-room è la fonte autoritativa. I documenti vivono sotto tickets/<AREA>/<YYYY>/<CASE_ID>/. Un builder Python valida i metadata, ricostruisce il registry e genera un sito statico deployabile. Aruba è esclusivamente il layer pubblicato.

STRUTTURA FINALE REPOSITORY
- tickets/AREA/YYYY/CASE_ID/: fascicoli autoritativi TXT.
- tools/build_data_room.py: validazione, risoluzione revisione REQUEST, STATUS derivato, registry e build.

- dist/: output generato in CI, non fonte autoritativa.

PROTOCOLLO CASE_ID
Il CASE_ID resta definito dalla Direzione Centrale. La directory del fascicolo deve coincidere con CASE_ID/AREA/anno dichiarati nei metadata. REQUEST, RESPONSE e DECISION vengono validati per coerenza AREA/TOPIC con il REQUEST attivo.

RISOLUZIONE CASE_ID → REQUEST
Il builder riconosce REQUEST.txt come revisione 1 e REQUEST_V<N>.txt come revisioni successive immutabili. Se esistono più revisioni, la revisione numericamente più alta è il REQUEST attivo. In pubblicazione viene creato l'alias stabile:
/data-room/cases/<CASE_ID>/request.txt
Per IMC-ENG-002 il REQUEST storico originale è stato preservato e la nuova richiesta operativa è stata registrata come REQUEST_V2.txt, senza alterare REQUEST.txt.

GESTIONE RESPONSE
La RESPONSE viene salvata nello stesso fascicolo del CASE_ID e non modifica il REQUEST. Il file corrente è tickets/ENG/2026/IMC-ENG-002/RESPONSE.txt. Il validator richiede gli stessi CASE_ID, AREA e TOPIC del REQUEST attivo.

GESTIONE STATUS
Lo STATUS non è mantenuto manualmente in un registro condiviso. È derivato dai documenti: solo REQUEST = OPEN; presenza RESPONSE senza DECISION = WAITING_REVIEW; DECISION può dichiarare STATUS con un valore ammesso, altrimenti chiude il fascicolo come CLOSED. Il registry può quindi essere rigenerato integralmente.

REGISTRY E RICERCA
Il build genera data/registry.json e data/registry.csv. Il JSON contiene almeno CASE_ID, AREA, DATE, TOPIC, STATUS, REQUEST attivo e documenti del fascicolo. La UI V1 permette ricerca per CASE_ID/testo e filtri AREA, DATE, TOPIC, STATUS, con apertura del REQUEST attivo, CASE JSON e documenti RESPONSE/DECISION quando presenti.
